# SC-03.5 — Customer Appointment Journey

Status: implementation workstream opened from the verified SC-03.4 head. This document is an implementation contract, not a completion claim.

## Starting point and source audit

- Parent: SC-03.4 PR #241, head `41d243ce2dd721886dd7faca4d92483b9356b26f`.
- Existing customer channel to extend: `app/store.html` + `app/store.js`.
- Existing buyer identity: `app/src/telegram-buyer-storefront.js` and `app/src/platform/telegram-buyer-identity-contract.js`; the server verifies Telegram WebApp `initData` against the seller-owned bot credential.
- Existing buyer history: `GET /api/telegram-storefront/:chatId/orders`, backed by `listTelegramBuyerOrders(chatId, telegramUserId)`. It is seller-scoped and does not expose tracking-token material.
- Existing booking authority: `createServiceBooking`, `transitionServiceBooking`, and `listServiceBookings`, under canonical seller order + service-line scope.
- Existing resource authority: `listServiceResources`, `getServiceResourceAvailability`, and SC-03.4 `service_resource_commitments`.
- Existing resource feasibility contract assesses declared working hours only. It explicitly does not prove availability, authorize, or commit. SC-03.4 adds the transaction-time overlap and schedule recheck that makes confirmation conflict-safe.

## Goal

Extend the existing Telegram buyer **My orders** journey so an authenticated buyer can discover appointment-based service lines in their own seller order, inspect time feasibility, submit a booking request, inspect booking status/resource details, and cancel only when the canonical booking lifecycle permits it.

Do not create another buyer identity, order history, booking ledger, resource registry, availability authority, or appointment lifecycle.

## Required customer journey

1. **My orders** continues to load using verified Telegram `initData`; client-supplied Telegram user IDs are never authorization input.
2. Each seller order exposes only its own service lines that the existing catalog/order projection confirms are appointment-bookable.
3. Buyer selects a service line, requested start/end, appointment mode, and optional note.
4. A read-only feasibility check returns a truthful state:
   - `FEASIBLE`: at least one active matching resource's declared hours contain the interval and no current committed interval overlaps.
   - `CONFLICT`: known matching resources cannot serve that interval.
   - `UNKNOWN`: missing/invalid schedules, timezone ambiguity, unavailable dependency, or incomplete resource evidence.
   Feasibility is advisory only. It is never a reservation or confirmation.
5. Buyer submits a request. Server re-verifies buyer identity, resolves the marketplace order to the seller's canonical order, verifies the buyer owns that order through the existing seller-scoped Commerce records, validates the service line, and creates a `REQUESTED` booking through the existing service booking authority.
6. Buyer sees canonical booking status, requested interval, appointment mode, and committed resource name only when the backend has actually committed one.
7. Buyer cancellation is available only for lifecycle states explicitly permitted by the server-side buyer-cancellation policy. No client-side status check is sufficient authorization.

## Proposed HTTP surface

All routes are Telegram storefront buyer routes. They must use the existing published-storefront check, `order_status` capability, secure seller credential resolution, and `verifyTelegramBuyerInitDataWithSecret` pattern. Derive buyer identity from verified `initData`, never from body/query identity fields.

- `GET /api/telegram-storefront/:chatId/orders/:marketplaceOrderId/service-bookings`
  - Return only seller-order bookings belonging to the verified buyer and this seller.
  - Include service-line display data, booking status/version/time/mode, status reason where customer-safe, and committed resource display name when committed.
- `GET /api/telegram-storefront/:chatId/orders/:marketplaceOrderId/service-feasibility?service_item_id=…&start=…&end=…&mode=…`
  - Read-only assessment across active resources matching the service and canonical location scope.
  - Never create a commitment, booking, hold, or audit-success claim.
  - Distinguish `FEASIBLE`, `CONFLICT`, and `UNKNOWN`; include a safe reason code and timezone used.
- `POST /api/telegram-storefront/:chatId/orders/:marketplaceOrderId/service-bookings`
  - Accept service item, requested interval, mode, note, and idempotency key.
  - Resolve and verify the seller order and buyer ownership server-side.
  - Call existing `createServiceBooking`; resulting state is `REQUESTED`, not `CONFIRMED`.
- `POST /api/telegram-storefront/:chatId/orders/:marketplaceOrderId/service-bookings/:bookingId/cancel`
  - Verify buyer ownership of the parent marketplace order, seller order, and booking.
  - Apply a narrow buyer-cancellation transition through existing `transitionServiceBooking`, with expected version and idempotency.
  - Initial policy: allow cancellation only in `REQUESTED` and `ACCEPTED` unless source-level lifecycle review proves a safe existing rule for later states. Do not release a committed resource outside the canonical transition transaction.

Route names are provisional until checked against the router's ordering and existing handler conventions. Prefer a minimal surface and shared helper over duplicate auth logic.

## Authorization and tenant isolation invariants

- Storefront must be published and the existing `order_status` capability enabled.
- Verify raw Telegram `initData` server-side using the seller-owned credential provider; do not trust `initDataUnsafe` or a body `buyer_id`.
- Scope every order lookup by seller ID and verified buyer identity.
- Resolve marketplace seller order to the canonical tenant/order using stored linkage; never accept a client-supplied canonical order ID as proof.
- Scope every booking lookup by organization, tenant, canonical seller order, and verified buyer ownership.
- Preserve canonical location/resource authorization and tenant boundaries.
- Do not return other sellers' bookings, internal resource metadata, provider personal data, credential references, audit internals, or tracking token/hash material.
- Server authorization is authoritative; UI visibility is convenience only.

## Customer UI requirements

Extend the existing `My orders` modal; do not create a parallel customer account or order screen.

- Each order card shows service line(s) and an **Appointments** section only when relevant.
- Provide an appointment request panel with service, date, start/end, mode, optional note, feasibility result, and submit action.
- Show a clear advisory label: feasibility is not a confirmed appointment; the provider must accept and commit a resource.
- Render booking lifecycle, requested interval, and committed resource only from server response.
- Offer cancellation only when server-provided allowed actions include it; server still rechecks.
- Preserve responsive/mobile Telegram WebApp layout and existing buyer chrome.
- No false success: request submitted means `REQUESTED`, not confirmed.
- States required: Loading, Ready, Empty, Offline Queued (not used for this online-only mutation; explain retry rather than queue), UNKNOWN/Stale, Error/Denied, and conflict.
- On network failure or stale version, retain safe form values and offer refresh/retry without claiming the mutation succeeded.

## Regression acceptance

### Backend / HTTP
- Valid buyer can read only their own seller-scoped service bookings.
- Valid buyer can request a booking only against a service line in their own canonical order.
- A product line, unrelated order, another buyer's order, another seller's order, wrong tenant, or forged buyer ID is denied.
- Invalid/missing/expired Telegram `initData`, unpublished storefront, disabled capability, and unavailable credential provider fail closed.
- Feasibility handles matching resources, service-specific resources, organization-wide resources, location scope, declared hours, overlapping commitments, empty schedules, invalid timezone, and unknown dependency state.
- Feasibility does not write booking, commitment, or success audit rows.
- Booking request is idempotent and remains `REQUESTED`; it never assigns a resource.
- Cancellation succeeds only in allowed states, is idempotent, and releases a commitment only through the canonical transition path where applicable.
- Cross-tenant/cross-seller/cross-buyer booking IDs do not disclose existence.
- No mutation to Commerce order status, Payment, Inventory, Fulfillment, or Logistics.

### Browser
- Existing My Orders still works.
- Service order displays appointment section; product-only order does not.
- Buyer can request and view a booking.
- Feasibility conflict/unknown states are distinguishable from success.
- Cancellation is hidden when not allowed and denied safely if a stale client attempts it.
- Mobile/desktop layout, escaping, keyboard operation, and no browser runtime errors.

### CI
- Add focused Node 24 regression scripts to the existing baseline/CI sequence.
- Re-run the relevant Telegram buyer regressions and service booking/resource regressions.
- Report results against the exact resulting commit SHA; do not inherit SC-03.4 CI status as proof for SC-03.5.

## Explicit non-goals

- No resource commitment at customer request time.
- No universal reservation/scheduling service.
- No separate buyer/customer identity, account, order, or appointment database.
- No automatic payment, refund, inventory, fulfillment, delivery, or Logistics side effects.
- No reschedule/no-show/deposit workflow until separately specified and backed by existing authority.
- Do not merge PR #241 or change its draft status as part of SC-03.5.
